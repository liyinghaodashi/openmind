# OpenMind 技术方案：以 Markdown 为源文件的 macOS 思维导图

日期：2026-09-19  
状态：原始总体设计基线，包含尚未实现的规划，不作为当前功能清单；当前已完成 v0.3 开发归档，实际功能、验证状态和边界以 [README.md](README.md) 与 [v0.3 交接说明](版本/v0.3.md) 为准。工具链安装由用户手动执行。

## 1. 结论与已确认约束

推荐方案：**Go + Wails v2 + 原生 HTML/CSS/JavaScript + HTML 节点与 SVG 连线 + Markdown 原文补丁编辑 + macOS FSEvents**。

应用直接打开用户选择的目录，目录内的 `.md` 文件就是正文的持久化来源。思维导图是 Markdown 的可编辑视图，不另存一份 JSON 正文再定期导出 Markdown。

用户已经明确：

- 首期只支持 macOS；后端使用 Go；前端不使用 React、Vue 等框架。
- 允许使用 SVG 连线，重点是以 Markdown 为源文件。
- 页面修改能够写回 Markdown；外部程序修改 Markdown 后，页面能够自动更新。
- 每次有效内容输入立即发起写入，每个编辑版本按顺序写入 Markdown；不等待停止输入，不合并或跳过中间编辑版本。应用不提供保存按钮、保存菜单或保存快捷键。
- 用户选择一个根目录，支持嵌套目录，并在前端展示真实目录关系。

本次项目目录为空，收到的是思维导图与 Markdown 预览的截图，**未收到可读取的 Markdown 源文件**。截图不能确定实际标题级别、空行、缩进和 Markdown 扩展；第 4 节给出的是拟议规则与重建样例，不宣称与原文件逐字一致。

需要先说明三个边界：

1. Markdown 定义内容和层级，但不原生定义节点坐标、颜色、折叠状态及任意关联线。首期采用自动布局，视图状态独立保存。
2. 任意 Markdown 的无损结构编辑并不简单。首期应明确支持的结构，其他内容保留原文，不能因导图不支持就删掉。
3. 文件监听不提供文件事务。对不参与锁定或文件协调的外部编辑器，无法承诺并发写入绝不覆盖；应通过冲突检测、恢复副本及明确的并发限制降低风险。

以下未确认的产品选择按建议方案展开，实施前再确认，不视为已经批准：首期单窗口/单工作区、主要支持本地磁盘、Markdown 方言、拖拽转换规则、最低 macOS 版本和发布渠道。

## 2. 技术选型

| 层次 | 建议 | 原因与边界 |
| --- | --- | --- |
| 桌面容器 | Wails v2 稳定线，开发时固定版本 | 与 Go、原生 JS 匹配，提供窗口、原生目录选择及 Go/JS 通信 |
| 界面 | HTML、CSS、原生 ES Modules | 按模块拆分状态、渲染与交互；不引入前端框架 |
| 构建工具 | Vite 可选，建议用于开发构建 | 构建工具不是 UI 框架；最终应用不要求用户安装 Node.js |
| 节点/连线 | HTML 节点 + SVG 连线 | HTML 处理文字、输入和可访问性；SVG 绘制曲线，便于调试 |
| Markdown | Go 中统一解析，优先评估 Goldmark | 解析和结构校验集中在后端，避免前后端两套语法解释 |
| 文件监听 | FSEvents，封装为内部 Watcher 接口 | 符合仅支持 macOS、递归目录监听的需求 |
| 文件写入 | 原文区间补丁 + 同目录临时文件原子替换 | 保留未修改字节，避免直接截断覆盖文件 |
| 正文存储 | 用户工作区中的 Markdown | 不需要正文数据库，不要求导出才能使用其他编辑器 |
| 本地状态 | Application Support 中的小型 JSON 与恢复文件 | 保存工作区配置、折叠状态、未保存草稿；缓存可以重建 |
| 日志与性能 | Go 标准日志、pprof、浏览器 Performance API | 记录阶段耗时与版本，不记录正文 |

Wails 官方提供 Vanilla JS 模板及 Go/JS 调用能力。调研时 v2 文档显示 v2.15.0，官网显示 v3 仍处于 beta；这里推荐 v2 稳定线，具体小版本在实施时固定，不使用浮动 latest。多窗口等需求若成为必要条件，再评估 v3。[Wails v2 文档](https://v2.wails.io/docs/introduction/)、[Wails 官网](https://wails.io/)

Goldmark 当前主分支已介绍 v2 的 CST 与位置记录能力，同时说明仍处于早期发布阶段。**不能把 v2 的能力当作 v1 已有能力，也不能把 CST 等同于已经验证的逐字节往返保证。** 首个技术验证应比较成熟 v1 加自有区间索引与 v2 的实际保真能力，再固定主版本；下面的设计不依赖某个尚未验证的 CST API。[Goldmark 官方说明](https://github.com/yuin/goldmark)

不选择 Electron，是因为会引入额外的 Chromium/Node 运行时与 Go 进程通信；不优先选择 Tauri，是因为当前已经确定 Go，增加 Rust 壳会增加维护面。这是本项目的取舍，不代表它们不适合桌面开发。

## 3. 总体架构

```text
用户选择的工作区目录
  ├─ GoLang.md
  └─ 后端/
      └─ Java.md
        │ 读取 / 原子替换                  │ FSEvents 变更提示
        ▼                                 ▼
FileStore                            Watcher + Reconciler
        │                                 │
        └──────── DocumentSession ────────┘
                  每份打开文档的串行处理入口
                  原文 / 版本 / 原文区间 / 导图树 / 恢复记录
                            │
                     Wails bindings + events
                            │
                 前端 Store / 命令队列 / 版本校验
                            │
                布局计算 → HTML 节点 + SVG 连线
```

Go 是正文状态、解析规则和文件写入的统一入口；前端持有后端状态的投影，以及尚未确认的本地输入。磁盘是已保存内容的持久化来源，内存中的未保存编辑必须有明确状态，不能称为“已经保存”。

前后端不需要自行建立 HTTP 服务或 WebSocket。请求走 Wails 绑定，通知走事件。事件只承担通知职责，应用协议自行处理版本、缺口和重连。[Wails 运行时事件](https://wails.io/docs/reference/runtime/events/)

按职责保留六个内部模块即可：

| 模块 | 负责 | 不负责 |
| --- | --- | --- |
| Workspace | 根目录授权、文件树、路径边界、文件操作 | Markdown 语义 |
| Document | 会话、版本、命令排序、撤销与冲突状态 | DOM 和操作系统监听细节 |
| Markdown | 语法解析、原文区间、导图映射、结构编辑校验 | 文件提交队列 |
| FileStore | 一致性读取、条件检查、文件替换、恢复副本 | 导图布局 |
| Watcher/Reconciler | 合并变更提示、扫描、读取最新内容 | 将事件直接翻译成正文修改 |
| Frontend | 输入、布局、局部渲染、可视状态 | 自行重写磁盘或重新解释 Markdown 层级 |

## 4. Markdown 与导图的映射

### 4.1 建议的首期规则

| Markdown 结构 | 导图行为 | 写回规则 |
| --- | --- | --- |
| 第一有效块为唯一一级标题 | 作为可编辑中心节点 | 修改标题文本，不自动改文件名 |
| 无一级标题、多个一级标题，或一级标题前有普通正文 | 用文件名作为虚拟中心节点 | 虚拟节点不写入正文；一级标题作为分支 |
| 二至六级标题 | 按标题栈形成层级 | 父节点为最近的更低级标题；跳级不生成虚构节点 |
| 无序/有序列表 | 列表项成为节点，按语法解析后的嵌套关系形成子节点 | 继承现有标记和缩进，不能靠固定空格数猜层级 |
| 标题下的段落 | 附属于该标题的正文/备注 | 不自动转成标题；可在备注区编辑 |
| 列表项第一段及后续段落 | 第一段作为标签，后续内容作为备注 | 不拆坏列表项原有块结构 |
| 代码块、引用、表格、图片 | 原文保留，作为附属内容或只读内容块 | 首期不提供复杂结构拖拽 |
| 粗体、行内代码、链接 | 标签支持有限内联展示 | 编辑时显示行内 Markdown 源文本，避免丢掉标记 |
| Front matter、HTML、未知扩展 | 原文保留，不作为可执行内容 | 不认识的块只读，不自动格式化 |

“第一有效块”允许忽略 BOM、空白、已识别的 front matter 和注释。根标题规则、备注显示方式需要用真实样例验证。

无损兼容与可编辑是两个不同概念：可保留任意未知字节，不意味着能安全地对所有未知结构执行移动、降级或合并。

### 4.2 按截图重建的拟议样例

下面仅用于讨论结构映射，不能替代用户原始 Markdown：

```markdown
# GoLang

## Go Modules

### 相当于 Maven / Gradle

## go.mod

### 相当于 pom.xml

## 编译运行

### 编译

- go build

  - GOOS=linux GOARCH=amd64 go build -o server

### 运行

### CGO

  - 本质上是一个开关，用于开启CGO

## 工程化

### internal

```

样例中的文字只是截图内容，不是本项目的运行命令或编译配置。实际 macOS 桌面集成可能需要 CGO，不能因为样例中有 `CGO_ENABLED=0` 就采用该构建参数。

### 4.3 新建与结构编辑

- 新建文件默认采用一个一级标题作为中心节点；标题下创建子节点优先生成下一级标题。
- 标题最多六级，第六级以下新建子节点使用列表；列表下新建子节点仍使用嵌套列表。
- 标签编辑首期用 textarea 编辑行内 Markdown；每次有效 input 立即提交，普通 Enter 结束节点编辑，不承担保存职责。组合输入期间不提交临时拼音，确认文字后立即提交。多段正文放备注区。
- 标题换父节点要连同所属 section 移动，并检查后代标题层级；列表移动要重算容器缩进。
- 首期只支持语法类型兼容的移动。标题拖进列表、移动后超过六级、涉及复杂嵌套块等情况拒绝并解释，不静默重写成另一种格式。
- 任意跨节点关联线、手动坐标排布、节点专属样式不进入首期正文模型；如果后续需要，应单独制定可移植元数据规范。

### 4.4 保留原文，而不是解析后重生成全文

内存中同时保留：原始 UTF-8 字节、语法树、导图投影，以及可以安全修改的原文范围。

每个结构节点至少区分：

- 标签区间：真正可编辑的文字部分。
- 块区间：包含本块的语法标记、换行与必要缩进。
- 子树区间：包括该节点拥有的后代及附属内容，供移动/删除使用。
- 编辑能力：可改标签、可插入、可移动、只读等，不由前端猜测。

标题的语法 AST 节点通常不直接包含完整 section；列表项可能包含多个段落、引用和代码块。需要额外构建所有权与区间索引，不能用一段简单正则完成安全写回。

例如修改 Go Modules，只替换相应标签范围。其他空行、CRLF/LF、列表标记、缩进、注释和未知块保持原字节。对结构操作，改动局限于受影响子树及必须调整的分隔符；遇到跨区域引用定义等依赖，先校验依赖，无法安全处理则禁止该操作。

一组补丁用同一个基础版本的半开字节区间表示，必须互不重叠，按偏移从大到小应用。应用后重新解析并验证意图，失败则保留旧正文。中文和 emoji 的 Go UTF-8 字节偏移与 JS UTF-16 下标不一致，因此前端传节点 ID 和新文本，字节区间由 Go 计算。

零编辑打开再关闭，不能发生自动保存或任何正文变化。首期接受 UTF-8（含 BOM），保留换行习惯；非法编码进入只读并提示，不能偷偷转换编码。

## 5. 文档身份与同步协议

### 5.1 身份和版本

| 字段 | 含义 |
| --- | --- |
| workspaceId | 本机工作区标识，与规范化根目录/授权信息关联 |
| documentId | 当前应用识别的逻辑文件身份；路径变化时尽量保持 |
| sessionId | 每次打开文档建立的新会话，屏蔽旧页面/旧任务消息 |
| nodeId | 会话内的结构节点身份，不使用行号或文本哈希充当唯一 ID |
| bufferVersion | 后端接受正文变化后递增的版本 |
| savedVersion | 已成功保存的 bufferVersion，可落后于 bufferVersion |
| diskHash | 最近确认的磁盘原始字节 SHA-256 |
| clientSeq/opId | 客户端顺序与操作去重标识 |

版本只在同一 sessionId 内有意义；哈希用于内容比较，不用修改时间充当版本。

纯 Markdown 没有稳定节点 ID。应用内编辑可以确定性沿用 ID；外部编辑用位置补丁映射、父子结构和相邻内容做保守匹配。存在重名、整体重排或匹配歧义时重新分配 ID，丢弃相关选择/折叠映射，而不是把本地修改套到错误节点上。不承诺跨任意外部改写永久保持节点身份，也不默认向正文注入隐藏 ID 注释。

### 5.2 请求与返回

拟议业务接口如下，属于设计接口，不是 Wails 内置 API：

```text
SelectWorkspace() → workspaceId, rootInfo, treeVersion
ListDirectory(workspaceId, directoryId, cursor) → entries, nextCursor, treeVersion
OpenDocument(workspaceId, fileId) → Snapshot
ApplyCommand(sessionId, baseVersion, clientSeq, opId, command) → Accepted | Rejected
AwaitPersistence(sessionId, upToVersion) → Saved | Conflict | Error
ResyncDocument(sessionId, knownVersion) → Patch | Snapshot
ResolveConflict(sessionId, conflictId, expectedDiskHash, resolution) → Result
```

首期命令至少包括 SetLabel、InsertSibling、InsertChild、DeleteSubtree、MoveSubtree。删除子树在产品中显示影响范围，并作为一次撤销事务。

前端同一文档最多一个尚未获得 Accepted 的命令；收到 Accepted 后即可提交下一条，不必等待该版本的 Saved。等待期间后续输入逐条留在本地队列，不合并标签修改，不丢弃或换序；下一条以最新确认的 bufferVersion 提交。后端每接受一个编辑版本，就立即把该版本的不可变正文或可精确重建它的补丁加入持久化队列，逐版本写入目标 Markdown，禁止只保留最后一版。

后端按 opId 缓存处理结果，重复调用返回原结果及最新持久化状态，不重复保存；缓存失效或会话变化后要求重新同步，不能盲目重放。AwaitPersistence 只供退出、会话释放等生命周期流程等待已经自动发起的写入，不是手动保存入口。

通知数据至少包含 sessionId、fromVersion、toVersion、origin、opId（适用时）与变更内容。Saved 通知携带准确的 savedVersion 和 diskHash；目录变化走独立 treeVersion。

前端只接受当前会话且 fromVersion 与当前确认版本一致的补丁。收到重复/旧版本则丢弃；发现缺口就拉取快照。调用返回与事件可能先后到达，不以到达顺序判定版本。订阅先建立再获取快照，并缓冲期间事件，依据版本去重，避免初始化丢更新。

Wails 事件没有被本方案当作持久消息队列使用。页面重载、恢复前台或通信异常后必须能重新拉取状态。

### 5.3 保存状态

```text
clean → 本地输入 → pending → 后端接受 → dirty → saving → clean
                                               │          │
                                      外部变化 → conflict  └─仍有新输入→ dirty
                                      写入失败 → error
                                      文件删除 → missing
```

Accepted 只代表后端接受修改，不代表已保存。界面不提供任何保存操作；可以低干扰地显示写入状态，并在失败时明确提示。只有本地队列为空、没有未确认命令、savedVersion 等于 bufferVersion，且没有冲突或错误，才能显示“已同步到文件”。dirty 是内部短暂状态，不要求用户做保存动作。

## 6. 双向同步的具体实现

### 6.1 页面修改 → Markdown

1. 用户输入立即更新当前编辑控件，确保打字不等待磁盘。
2. 每次有效 input 立即生成独立命令，无 debounce、throttle 或等待下一帧的保存调度。中文输入法在确认文字后提交；根据 compositionend 与最终 input 的实际事件顺序去重，一次确认只提交一次，不能把中间拼音写进文件。
3. Go 检查 sessionId、baseVersion、节点身份和编辑能力；基础版本过期则拒绝并携带最新状态，不猜测目标。
4. 为受影响范围生成原文补丁，重新解析校验，成功后更新内存正文和导图树，递增 bufferVersion。
5. 把该版本加入持久化队列并立即唤醒写入器，再返回 Accepted 及权威补丁；前端更新已确认基线，并保留后续输入。
6. 写入器空闲时立即开始；已有写入时按序排队，上一版完成后立即执行下一版，无人为等待窗口。依次执行第 7 节写入流程，每个有效编辑版本都替换到目标 Markdown。
7. 每次成功仅确认实际写入的 savedVersion；后续输入保持待写入状态。不能把只进入恢复日志、缓存或内存的版本当作目标 Markdown 已更新。

例如依次输入 a、b、c，对应正文版本 a、ab、abc：目标文件必须依次提交这三个版本，不能将它们合并成一次 abc 写入。系统监听可能合并通知，外部观察者不保证看到每个中间版本，但本应用不能主动省略写入。

例如版本 10 正在保存时内存已编辑到 12：保存 10 成功后，磁盘共同基线推进到版本 10，再写版本 11，然后写版本 12。每次检查的是上一个成功提交版本的磁盘哈希，不能误判自身写入为外部冲突。期间发现真实外部修改则停止后续提交并保留整条本地队列，不强行把剩余版本写完。

“一次有效输入”指一次已确认的内容变更：英文正常输入通常一次一个字符，输入法一次确认的词句、粘贴、删除、撤销或结构操作各形成一次编辑事务；不把一次粘贴人工拆成逐字符保存。输入期间尚未闭合的行内 Markdown 也要原样保存，不能等语法完整或结束编辑才写回；前端保留编辑锚点，投影变化不得销毁正在输入的控件。

Enter、失焦和切换文件不是保存触发条件；内容早已在各次输入时提交。应用不注册 Cmd+S 等保存快捷键，不设置保存按钮或菜单。切换视图不销毁待写入会话，正常退出自动等待提交队列排空；遇到失败才展示异常处理，不询问用户是否保存。不能用前端 beforeunload 临时异步写文件作为可靠退出机制。

即时保存意味着每次输入都立即启动持久化流程，不意味着磁盘 I/O 零延迟。输入回显到写入成功之间仍存在短暂窗口；若要求屏幕上出现的每个字都已经落盘，就必须等写入确认后再显示，会直接增加打字延迟，本方案不采用这种交互。

### 6.2 外部修改 → 页面

1. FSEvents 返回变更提示，只把路径/目录加入待核对集合；回调中不读大文件、不解析 Markdown。
2. 按路径合并约 50–100ms 的重复提示；繁忙时设置最大等待时间，并让当前打开文档优先。
3. Reconciler 根据当前真实目录状态处理创建、删除、替换或移动，读取候选文件。临时消失先短暂重试，区分原子替换与真正删除。
4. 对文件描述符前后取状态，并核对当前路径对应身份，必要时重复读取；若仍在持续变化则延迟应用。两次相同读数只是稳定性启发式，不代表拿到跨进程锁。
5. 对读到的原始字节计算哈希。与当前确认磁盘基线相同就无需重复解析；不同则是真实内容变化，包括改回历史版本。
6. 没有本地未保存变化时，更新基线、重新解析、生成树差异并通知前端；前端局部更新节点和布局。
7. 有本地未保存变化时进入冲突流程，不能直接覆盖输入控件或自动用本地内容盖掉磁盘。

接受外部内容也是一次新的 bufferVersion；该版本直接对应已观察到的磁盘内容，因此同步推进 savedVersion 和基线，但不产生保存任务。若正处于本应用保存提交期间，外部读取结果先经过提交代次检查，提交结束后重新核对，避免在自身替换与状态登记之间错误制造冲突。

外部文件暂时写了一半时，尽量保持上一个稳定视图并展示“文件正在更新”。Markdown 通常宽容解析，能解析成功不表示外部程序已经写完；对于持续输出文件，首期不承诺每一个中间状态都实时展示。

若后端认为文档干净，但前端还有尚未提交的输入，前端收到外部版本后保留这部分草稿，停止自动提交，进入“基于旧版本的输入待处理”状态；不能因为尚未到达 Go 就当作不存在。

### 6.3 防止自身写入形成循环

不能采用“保存后忽略 500ms 文件事件”，因为这会吞掉真实外部修改；也不能永久忽略任何曾经由自己写过的哈希，因为外部可能主动恢复到旧内容。

采用以下规则：

- 保存成功后记录当前已提交的版本与磁盘哈希；监听提示仍然正常核对。
- 读到与当前磁盘基线完全相同的字节，视为无需变化，不触发新保存。
- 与当前基线不同就按新外部状态处理，即使其哈希曾在过去出现过。
- 外部导入与视图刷新本身不产生写回命令；只有明确用户编辑或明确冲突解决动作才产生保存。
- 读任务捕获会话 generation 和磁盘基线代次，结果返回时若代次变化则重新核对，不能把旧读结果覆盖到新保存之后。

文件事件不带本应用的 opId，origin/opId 只用于应用协议。自身写入的判断来自内容核对与提交状态，不来自对操作系统事件来源的猜测。

### 6.4 冲突处理

保留三个版本：B 为本地修改起点的共同基线，L 为包含未保存命令的本地正文，R 为最新磁盘正文。

| 情况 | 行为 |
| --- | --- |
| L 与 B 相同 | 直接接受 R |
| R 与 B 相同 | 本地可以继续按条件保存 L |
| L 与 R 相同 | 标记内容已一致，核实对应版本后消除 dirty |
| 双方都不同 | 首期进入冲突状态，保留 B/L/R，暂停自动保存 |

首期建议不自动合并双方编辑。应用自动保留冲突副本，用户可以选择采用磁盘版本、保留两份或采用本地版本。选择完成后自动执行对应处理，不再追加保存步骤；这属于冲突处理，不是日常保存入口。覆盖前再次检查 expectedDiskHash；磁盘又变化就更新冲突，不覆盖新版本。

后续再增加三方合并：仅自动合并能够证明互不干扰的原文改动，并在合并后重解析校验语义。不同字节区间不等于语义无冲突，例如前面新增代码围栏会改变后面的解释；标题移动与子节点修改也可能互相影响。同节点改名、删除与编辑、重排与移动冲突应交给用户。

不要把冲突标记直接写进原 Markdown，让正常阅读受损。恢复副本自动存应用私有目录，用户选择“保留两份”时才在工作区创建新的可见 Markdown。

外部版本被接受后设置撤销边界。撤销本地操作应该生成针对当前版本的新命令；如果无法安全应用就停止，不能通过整篇旧快照把外部改动全部撤回。

### 6.5 并发和背压

- 每份打开文档一个串行状态机/任务队列；同一文档的命令、读取结果和保存结果必须经该入口处理。
- 不为工作区里每个文件建立一个常驻会话，未打开文件只维护目录索引。
- 阻塞 I/O、解析可以放有限工作池，但结果必须携带会话与任务代次，过期任务不能回写状态。
- 同一文档不允许多个保存同时执行；新的输入逐版本入队，各自立即调度，不能累积后只保存最终状态。
- 持久化队列设定版本数、占用字节与最老等待时长的上限，具体值由压测确定。持续积压时显示写入延迟，达到上限则暂停新的内容编辑并保留已有输入，排空后自动恢复；禁止静默改用防抖、跳过版本或无限占用内存。
- 监听事件采用有界去重集合。集合溢出时标记对应目录需要重扫，不让通道阻塞原生回调，也不假装没有丢事件。
- 外部读取的过期解析候选、前端可视布局任务可以取消；本地每个有效编辑版本的校验、保存及恢复记录不可因为更新版本到达就取消。画面允许按帧合并绘制，目标文件写入不允许合并版本。

## 7. 文件安全、恢复与保证边界

### 7.1 保存步骤

以下针对首期本地磁盘，同目录、同文件系统写入：

1. 从持久化队列头取得下一版本正文，并从状态机取得最近成功提交的磁盘基线；不选取最新版本跳过中间版本。
2. 重新读取目标并核对哈希；外部状态不同就转冲突。目标已删除则进入 missing，不擅自重建。
3. 在应用私有恢复目录保存本次替换前可见的正文和待提交正文，记录事务 ID、路径、版本与哈希；恢复记录写失败时暂停保存并报错。
4. 在目标同一目录创建随机命名的临时文件，完整写入新正文，检查写入错误，按既定策略保留文件权限及必要元数据。
5. 对临时文件 Sync、关闭；在最终替换前再次核对目标状态，变化则弃用本次提交并保留草稿。
6. 原子 rename/replace 到目标路径；不能先删除原文件。已有文件替换与新建文件的“不覆盖已存在目标”是两种不同操作，新建要用系统的独占/不替换语义。
7. 按 macOS 和目标文件系统实际能力处理父目录同步并检查结果，重新核对目标内容；记录提交结果，再通知 Saved。替换成功后同步失败属于“已替换但耐久性未确认”，不能当作从未写过而直接重试旧正文。
8. 标记恢复事务完成，后台按保留策略清理旧记录；清理失败不影响已经成功的正文保存。

Go 的 Rename 文档说明操作受平台约束；本设计不把它推广为跨文件系统、跨平台事务保证。[Go os 文档](https://go.dev/pkg/os/)

应用侧所谓“原文补丁”是逻辑编辑增量。物理保存仍然完整写出单个文件，不进行原地插入字节。这样换取读者看不到本应用写出的半篇内容；即时保存模式不能靠减少保存次数规避成本。优化应放在复用原文字节片段、减少内存复制、避免重复解析与局部绘制上，不能把目标 Markdown 延迟生成。

对于大小为 S 的文件和每秒 R 次有效编辑，仅目标文件完整替换的写入量约为 S × R，尚不含基线检查、恢复副本、元数据与 Sync 成本。例如 2MB 文件每秒 10 次编辑，目标数据写入就约为 20MB/s。每次文件同步的延迟也可能主导吞吐，必须单独压测。不能同时无条件承诺任意大文件、逐输入完整写入、低能耗和毫无延迟；超出能力时明确背压，不悄悄改变用户要求的保存语义。

### 7.2 原子替换解决不了什么

哈希检查与 rename 之间仍有竞争窗口：外部编辑器可能恰好在此时写入。文件锁通常只约束自愿遵守锁的程序；FSEvents 通知也不是实时写锁。

因此，首期承诺是：检测到分歧就不静默覆盖；保存前保留已观察到的旧内容和本地新内容；保存后再次核对。**不承诺能恢复一个从未被本应用读到、且在检查与替换之间被覆盖的外部版本。** “任意编辑器并发写同一文件且零丢失”不能作为当前方案已经满足的能力。

macOS 的 NSFileCoordinator/NSFilePresenter 可以协调参与该机制的应用，适合作为后续增强或 File Provider 支持的基础，但不能强制普通命令行写入者参与。[Apple 文件协调说明](https://developer.apple.com/documentation/foundation/nsfilecoordinator)

若用户要求严格并发零覆盖，应改变协作条件：编辑时建立双方遵守的独占/协调机制，或收口到统一写入服务。这属于产品约束，不是换一个监听库就能解决。

### 7.3 崩溃、断电与元数据

- 不设置自动保存等待窗口。每次有效输入立即进入提交路径，正常退出自动排空队列；尚未到达后端、尚未写出或尚未持久化确认的内容仍有崩溃丢失窗口，不能仅因“即时保存”就声称绝不丢字。
- 恢复记录包含完整校验与阶段标记；启动时比对目标文件、待提交版本和恢复事务，只在状态明确时恢复。状态不明确则让用户选择，不能自动覆盖磁盘新内容。
- 临时文件仅清理可证明由本应用创建且不再使用的项目，不批量删除用户目录中的其他临时文件。
- 原子替换会改变 inode，可能影响权限、ACL、扩展属性及硬链接语义；首期必须验证元数据保留。硬链接文件建议只读或要求另存，避免替换路径后悄悄断开共享关系。
- File.Sync 与 rename 不等于绝对断电安全。若需要更强的耐久性，应评估 macOS F_FULLFSYNC 与设备支持，并测量延迟，不作无条件承诺。[Apple fsync 手册](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/fsync.2.html)

## 8. 工作区、嵌套目录与监听

### 8.1 文件组织

```text
用户选择的文件夹1/
├─ GoLang.md
├─ 后端/
│  ├─ Java.md
│  └─ 数据库/
│     └─ MySQL.md
└─ 前端/
   └─ JavaScript.md
```

前端侧边栏直接映射磁盘目录。目录节点和 Markdown 文档节点是两类对象，不把文件夹误当成导图节点。

新增 Markdown 默认放在当前选中的文件夹内；未选中时放工作区根目录。首次重名时生成新名称或让用户选择，不能覆盖已有文件。文件名与文档根标题独立，不因改标题自动移动文件。

文件树按目录懒加载并分页，大目录使用列表虚拟化；后台可逐步建立轻量索引，但不在启动时解析所有 Markdown。隐藏目录默认不展示/不深入扫描，目录树可显示空目录；识别 `.md` 和 `.markdown`，扩展名判断不区分大小写。

### 8.2 为什么首选 FSEvents

FSEvents 原生按目录树通知，适合监听工作区根目录。fsnotify 在 macOS 使用 kqueue，其官方说明指出递归监听需额外处理，且文件描述符消耗随被监听项目增加；对于大工作区，不宜把它作为唯一实现。[fsnotify 官方说明](https://github.com/fsnotify/fsnotify)

可评估 fsnotify/fsevents 作为 Go 适配器，但需验证所固定版本的构建、回调生命周期、停止与重启行为；库不能通过验证时，再实现薄的原生桥接。保持 Watcher 接口稳定，业务层不依赖该库的数据类型。[fsnotify/fsevents](https://github.com/fsnotify/fsevents)

拟议监听参数从约 50–100ms latency 起测，并开启文件级事件和根目录变动检测。更低延迟会增加唤醒和处理频率，不能直接推导出更高整体性能。

### 8.3 必须处理的监听边界

- **先监听、后扫描**：先建立监听并缓存提示，再扫描初始目录，最后核对扫描期间受影响的路径，避免初始化间隙。
- **合并与丢失**：MustScanSubDirs、UserDropped、KernelDropped、EventIdsWrapped 等情况触发对应范围重扫；标志可能同时存在，不能写成互斥分支。
- **根目录失效**：根目录被移动、删除、卸载或授权失效时停写并显示脱机/重新定位状态；监听路径不会自动跟随任意目录迁移。
- **原子替换**：事件可能是删除、创建或重命名的组合，不能一见删除就丢弃当前编辑会话。
- **目录重命名**：按文件标识、路径和快照差异尽量识别；无法证明同一文件时按删除加新增处理，并保留原会话草稿。
- **事件只是线索**：定期低优先级核对目录快照，唤醒和恢复前台时立即核对。持久事件 ID 仅用于加速恢复，不能代替快照校验。

这些是对 Apple 事件模型的应用设计，具体标志与恢复路径应通过 macOS 集成测试验证。[Apple FSEvents 指南](https://developer.apple.com/library/archive/documentation/Darwin/Conceptual/FSEvents_ProgGuide/UsingtheFSEventsFramework/UsingtheFSEventsFramework.html)

### 8.4 路径与存储边界

- 前端只传工作区内部文件 ID/相对位置，由 Go 解析路径；不能提供可写任意绝对路径的通用接口。
- 路径验证必须处理 `..`、符号链接与中途路径替换，不能只用字符串前缀。首期不跟随工作区内的符号链接；根目录用户选定后解析并记录真实身份。
- 同时测试大小写敏感与不敏感 APFS、中文、emoji、Unicode 规范化及仅大小写改名；不能一律把路径转小写作为身份。
- 首期性能与一致性目标针对本地磁盘。iCloud、其他 File Provider、SMB、外置卷的事件和占位文件行为单独验证，不套用本地磁盘承诺。
- 打开文件不代表编辑器拥有文件删除权；外部删除且本地有草稿时保留草稿，提供另存，不自动复活被删除文件。

## 9. 前端渲染与性能

### 9.1 DOM 组织

```text
viewport（处理平移/缩放和可视区域）
├─ edges.svg（只包含可见区域相关连线）
├─ nodes-layer（按 nodeId 管理 HTML 节点）
└─ editor-overlay（当前节点的 textarea）
```

节点用 DOM 元素承载，避免整张图作为图片。编辑器浮层用 textarea，避免首期自制复杂 contenteditable 富文本编辑器。导图和文件树均提供键盘导航与焦点管理，折叠控件带明确的可访问名称。

### 9.2 只更新必要内容

后端比较新旧导图树，输出新增、删除、标签更新、父子关系更新；前端按 nodeId 保留 DOM，不在每个事件后重建整张图。

第一版后端可对发生变化的**单个打开文件全量解析**，然后做树差异；这比一开始自研完整增量 Markdown 解析更可靠。全量解析单文件与全量重建 DOM 是两回事。

测量证明解析成为瓶颈后，再评估区块重解析、行索引和文本缓冲结构。代码围栏、引用定义和列表边界可能影响远处语义，不能仅根据修改行解析一个固定小窗口。

### 9.3 布局算法与可见性

首期采用截图类似的单侧水平树布局，暂不扩展到鱼骨图、时间轴等多种布局。

1. 按文本、样式和宽度约束缓存节点尺寸。
2. 自底向上计算子树高度，自顶向下分配坐标。
3. 标签大小变化时将节点和祖先链标记为布局失效，只重算受影响区域。
4. 将位置变化集中在一帧提交，尺寸读取与样式写入分批执行，避免交替读写引发反复布局。

树布局可能因一个节点变高而移动大量后续兄弟，最坏情况仍为 O(N)，不能承诺所有编辑都是 O(1)。可对整组子树应用位移，并在实际访问时展开坐标变化。

逻辑树可以包含上万节点，但 DOM/SVG 只保留视口加缓冲区内的节点和相交连线，折叠分支直接跳过。可使用空间索引减少逐帧 O(N) 可见性扫描。编辑中的节点和焦点目标保持挂载，不能滚动时卸载正在输入的控件。

缩放和平移共用坐标变换；requestAnimationFrame 合并一帧内多次请求。SVG 连线数量很大时可评估 Canvas 连线，但先解决可视裁剪，不能把换 Canvas 当作万能优化。

必要时把纯布局运算迁到 Web Worker；DOM 测量仍在主线程，Worker 消息携带布局代次，丢弃过期结果。避免每个按键都复制整棵树进出 Worker，先用局部数据或可转移数值缓冲。

### 9.4 安全展示

普通标签使用 textContent；内联 Markdown 由受控 token 映射到允许的元素，禁止把原文直接塞进 innerHTML。禁用 Markdown 中的脚本、原始 HTML 执行和 javascript URL。相对资源通过受限的工作区资源访问层加载，默认不自动请求外部图片；点击链接再交给系统浏览器。

生产资源使用限制性 CSP，具体策略与 Wails 桥接加载方式一起验证，不能配置一个导致桥接失效的未经测试策略。

## 10. 性能目标与验证方式

以下是**工程验收目标，不是已经实测的数据**。基准机暂定 Apple Silicon、16GB 内存、本地 APFS、生产构建；实施时记录具体机型、系统版本、屏幕与 WebView 版本。

| 场景 | 初始目标 |
| --- | --- |
| 输入回显 | 主线程下一帧可见；60Hz 下单帧预算约 16.7ms |
| 常规文件：≤200KB、≤1,000 节点 | 外部稳定写入至页面更新 P95 ≤300ms |
| 常规文件逐输入保存 | 每次有效 input 至对应 Saved，初始目标 P95 ≤100ms；持续每秒 10 次编辑时队列不持续增长 |
| 逐输入语义 | 无保存等待定时器，每个有效编辑版本都有一次目标文件提交记录，不跳版本 |
| 同上文件首次打开 | 已获得文件权限后，内容首屏 P95 ≤300ms |
| 大文件：约2MB、10,000 节点 | 首次打开 P95 ≤1.5s；缩放平移不挂载全部节点 |
| 大工作区：10,000 个 Markdown | 优先显示根目录与已展开目录；不等待正文批量解析 |
| 静止工作区 | 无固定高频全量正文扫描，无持续布局循环 |

外部更新总延迟需要分别统计：系统事件延迟 + 合并等待 + 读取/哈希 + 解析/差异 + 桥接 + 布局/绘制。系统事件延迟可以在测试中通过受控外部写入程序埋点测量，不能只统计 Go 收到事件之后的时间。

保存总延迟包括前端发送等待、命令校验、持久化队列等待、恢复记录、正文写入与同步，不应只统计 rename。分别测试每秒 1、5、10、20 次有效输入及粘贴突发，记录吞吐、写入量、队列长度、最老版本等待时间及退出排空耗时。每份文档记录 bufferVersion、savedVersion、任务代次、字节数、节点数和阶段耗时，禁止记录用户正文。

分别测试重复标签、深链、大量兄弟、超长单行、代码块、中文/emoji 与大批量目录变化。P50/P95/P99 均保留；启动首屏、后台完整扫描和大文件降级状态分别报告。超过 2MB/10,000 节点先显示进度、支持取消，不宣称规模无上限。

## 11. macOS 集成与本地状态

首期建议直接分发签名和公证的 `.app`，是否使用 DMG 属于发布包装选择；是否进入 Mac App Store 尚待决定。

目录通过系统选择器取得。若采用 App Sandbox，需要持久化 security-scoped bookmark 并正确管理访问生命周期，过期后重新授权；非 Sandbox 场景仍需处理系统隐私权限和目录不可用。不能只保存一个绝对路径就认为永久可访问。[Apple 沙盒文件访问](https://developer.apple.com/documentation/security/accessing-files-from-the-macos-app-sandbox)

拟议状态位置：

```text
~/Library/Application Support/OpenMind/
├─ settings.json
├─ workspaces/<workspace-id>/view-state.json
└─ recovery/<document-id>/<transaction-id>/...
```

视图状态保存折叠、缩放、选择和最近打开文件，不是正文权威副本。恢复目录有明确大小/时间上限；未解决冲突不得按普通缓存自动淘汰。删除视图缓存后应能从 Markdown 重建可读导图，但不保证恢复旧选择位置。

首期限定同一工作区只有一个本应用写入实例，通过应用级工作区锁避免自己与自己竞争；锁不能当作约束外部编辑器的手段。支持 Intel 与 Apple Silicon 的范围以及最低系统版本需要结合真实用户设备决定；Mac App Store、云盘和多窗口都不是默认已完成项。

## 13. 实施顺序与验收

### 阶段一：验证最容易失败的假设

取得真实 Markdown 样例，确认标题/列表映射；在隔离测试目录验证原文区间定位和不修改部分的字节一致性。验证 Wails 原生 JS、FSEvents 递归监听以及外部编辑器原子替换后的持续监听。

这一阶段决定 Markdown 库主版本和实际 macOS 支持范围；任一关键验证失败，先调整方案，不进入大规模界面开发。

### 阶段二：只读闭环

目录选择 → 嵌套文件树 → 打开 Markdown → 自动树布局 → 外部编辑实时更新。覆盖启动扫描间隙、目录改名、删除、唤醒和监听溢出恢复。

### 阶段三：可靠编辑闭环

增加标签修改、新建节点、原文补丁、串行命令、逐输入即时保存、Saved 状态、冲突保留和崩溃恢复。验证整个界面无保存按钮、菜单或快捷键。首期冲突采用保守人工处理，解决后自动执行，无额外保存步骤。

### 阶段四：结构编辑与规模优化

增加明确允许的子树操作和撤销，再以真实剖析数据优化可视裁剪、布局、桥接和解析。完成 macOS 签名、公证及安装后文件授权验证。

### 必须通过的针对性测试

| 测试 | 验收条件 |
| --- | --- |
| 零编辑往返 | 打开/关闭不写文件，字节完全不变 |
| 标签补丁 | 仅允许范围改变，空白、换行、注释、未知块不受影响 |
| 中文/emoji/IME | 无字节错位，无拼音中间态提交，无外部更新打断输入 |
| 逐输入即时保存 | 连续 a→ab→abc 三次有效输入对应三次目标文件提交；不等 Enter、失焦或停顿 |
| 输入事件语义 | 输入法确认仅一次提交，粘贴/删除/撤销各自即时提交，不重复或漏交 |
| 未闭合行内语法 | 标签输入到半个链接或强调标记时仍然写回，编辑控件不被重建 |
| 无手动保存入口 | 不存在保存按钮、保存菜单与保存快捷键，正常关闭自动等待已有写入 |
| 写入背压 | 慢磁盘下版本不合并、不丢弃、队列有界；达到上限暂停新编辑并可恢复 |
| 重复标题与重排 | 不将操作应用到另一个同名节点，歧义可安全中止 |
| 外部保存两种方式 | 截断重写、临时文件替换都能更新且不丢后续监听 |
| 自身回声与历史恢复 | 自身保存不产生循环；外部改回历史内容仍然生效 |
| 真并发与前端待提交输入 | 分歧进入冲突，不因为后端暂时 clean 就丢掉前端草稿 |
| 旧读任务与旧事件 | 保存/切换之后的旧结果被丢弃或重新核对 |
| 写入故障注入 | 磁盘满、权限不足、Sync/rename 失败不误报已保存 |
| 中途崩溃 | 临时文件、替换前、替换后等阶段可解释恢复，不盲目覆盖 |
| 删除/改名/根目录失效 | 保留未保存编辑，不自动创建已被删除的原文件 |
| 监听丢失与过载 | 通过核对恢复最终状态，队列与内存有界 |
| 语法边界 | 围栏、引用定义、深层列表等不因局部优化产生错误语义 |
| 撤销跨外部更新 | 不用整篇旧快照撤回外部新内容 |
| 保存期间继续输入 | 仅确认实际保存版本，后续每个版本按顺序写入，不跳到最新版本 |
| 工作区路径边界 | 符号链接、路径穿越、大小写与 Unicode 不导致写错文件 |
| 大规模渲染 | 10,000 节点不会全部挂载，输入与平移按预算测量 |

测试中的文件写入/删除只发生在明确创建的测试目录，不能用用户实际 Markdown 作为故障注入材料。任何性能数据在完成测量前都只能作为目标。

## 14. 实施前待确认的产品决策

1. **真实 Markdown 方言与样例**：截图重建的“标题 + 列表”是否匹配现有文件；普通段落是否展示为备注。
2. **首期编辑范围**：是否接受先完成文字、增删和受限移动，复杂结构保留只读。
3. **并发修改要求**：是否接受检测到冲突即暂停自动保存；任意外部编辑器并发零丢失不在可承诺范围内。
4. **文件位置**：主要使用本地目录，还是首期必须支持 iCloud/其他云盘。后者会改变原生协调与验收范围。
5. **发行与设备**：直接分发还是 Mac App Store，最低 macOS 版本，是否需要 Intel。

技术文档可以先按这些建议推进讨论；正式实现前确认上述影响文件格式、数据安全和平台集成的决策。
