# 访达打开文件时的冷启动窗口显示延迟

日期：2026-10-18  
范围：macOS、Wails v2.15.0、OpenMind 打包应用，通过系统文件关联打开 Markdown。

## 1. 问题与结论

完全退出 OpenMind 后，在访达双击 `.md` 文件，Dock 图标立即出现，但约 5 秒后才能看到文档窗口。用户确认：只有冷启动慢，应用已经运行时打开其他文件没有同样的问题。

**本次延迟发生在原生窗口显示阶段。正文在约 0.44 秒时已经就绪，窗口却要到约 5.3 秒才出现在屏幕窗口列表中。** 修复是在前端启动初始化及首批文件打开处理完成后，再调用一次 Wails 的 `WindowShow()`。修复后，本机实测约 0.51～0.60 秒显示窗口。

这里的“冷启动”指应用进程完全退出后的重新启动，并不表示清空了操作系统文件缓存，也不是首次安装后的第一次启动。

## 2. 为什么会出现

### 原有启动流程缺少最后一次窗口显示请求

Wails v2.15.0 的 macOS 实现在 `applicationWillFinishLaunching` 中调用：

```objc
[self.mainWindow makeKeyAndOrderFront:self];
```

在 `applicationDidFinishLaunching` 中，再调用 `activateIgnoringOtherApps:YES` 激活应用。这些动作发生在原生应用启动阶段；前端编辑器初始化、接收系统文件打开请求、加载文档则在后续异步执行。

OpenMind 原有流程只依赖框架早期的显示请求。前端真正完成初始化和文档加载后，没有再次明确请求显示窗口。在本次复现的系统文件冷启动路径中，早期请求没有让窗口及时进入屏幕窗口列表，后续也没有应用侧的显示动作来解除这段等待。

```text
原有：系统打开文件 → 原生启动阶段请求显示窗口
                         ↓
                   前端初始化、正文就绪 → 继续等待窗口实际显示

修复：系统打开文件 → 原生启动阶段请求显示窗口
                         ↓
                   前端初始化、正文就绪 → 再次请求显示窗口
```

因此需要区分三个状态：

| 状态 | 能说明什么 | 不能说明什么 |
| --- | --- | --- |
| Dock 图标出现 | 应用已启动 | 文档窗口已经可见 |
| 页面 `readyState=complete`，正文 DOM 已有内容 | 页面加载及正文内容已经就绪 | 内容已经呈现在桌面上 |
| 原生窗口进入屏幕窗口列表 | 窗口已被系统列为屏幕上的窗口 | 所有正文像素、图片均已完成绘制 |

诊断时还观察到：`NSWindow.isVisible` 已经为真，但窗口的 `occlusionState` 尚未包含可见位，屏幕窗口列表也没有目标窗口。仅检查窗口对象的 `isVisible`，会误以为启动已经完成。

### 已确认的原因与证据边界

已确认的是：**早期窗口显示请求与实际显示之间存在延迟；在内容就绪后再次请求显示，可以消除本机复现的延迟。** 应用侧缺少这个启动收尾动作，是本次修复针对的问题。

尚未确认的是：macOS 内部究竟由哪个窗口排序、激活或启动协调机制产生约 5 秒的等待。没有证据证明这是固定的 AppKit 超时、Wails 的 5 秒定时器，或某个特定 macOS 版本的系统缺陷。也没有证据表明所有 Mac 都必然出现。

本次方案属于针对已验证窗口显示时序的兼容性修复，不宣称修改了 macOS 内部机制。

## 3. 如何定位和排除

先用 `NSWorkspace` 的系统文件打开接口启动已安装应用，再用 `CGWindowListCopyWindowInfo` 轮询目标进程的屏幕窗口。这样覆盖了打包应用、系统文件打开和原生窗口显示链路，不只测浏览器里的前端。

修复前，多种输入都稳定复现约 5 秒延迟：

| 输入 | 修复前窗口出现 | 修复后窗口出现 |
| --- | ---: | ---: |
| 只有标题和一行正文的 `.md` | 5261 ms | 582 ms |
| 项目 `README.md` | 5263 ms | 602 ms |
| `examples/灵感.mind.md` | 5242 ms | 512 ms |

这些是本机各场景的单次记录，不是跨设备平均值或性能保证。单独的原生回归脚本也在旧包上得到 `FAIL … 5282 ms`。

进一步的证据：

- **前端隔离测量：** 含 100 个章节和表格的测试文档，约 322 ms 完成前端测量流程。该测量不包含完整应用启动，不能直接等同于用户等待时间，但说明测试内容本身不需要约 5 秒。
- **已安装应用的临时诊断：** 以进程诊断入口为起点，437 ms 时页面已完成加载，正文 DOM 包含目标文件内容；窗口仍未实际进入屏幕窗口列表。该起点与系统启动计时起点不同，不能直接相减得出精确阶段耗时。
- **主线程采样：** 等待期间主线程大部分时间在事件循环中空闲，没有发现连续约 5 秒的正文计算阻塞。
- **单变量对照：** 页面就绪后调用原生 `makeKeyAndOrderFront:`，窗口显示降到约 511 ms；补发文件打开回复、尝试禁用状态恢复的诊断实验没有消除延迟。后两项仅排除了当时测试的具体方案，不代表完全排除所有系统内部相关机制。

这些证据足以把修复集中在窗口显示时序，无需改动 Markdown 解析、编辑器加载或目录扫描。

## 4. 如何修复

业务代码只增加了一个启动收尾调用，位于 `frontend/src/main.js` 的原生应用初始化分支：

```js
externalFilesReady=true;
await call('FrontendReady');
await receiveExternalFiles();
window.runtime.WindowShow();
```

前面已有的流程会等待设置和编辑器就绪，注册事件监听，领取启动期间缓存的文件请求；没有指定文件时恢复工作区。这里的第二次 `receiveExternalFiles()` 会处理已领取的请求，并补领初始化期间到达的请求，然后请求显示窗口。

Wails 的 macOS `WindowShow()` 最终执行：

```objc
[self.mainWindow makeKeyAndOrderFront:nil];
[NSApp activateIgnoringOtherApps:YES];
```

调用使用现有窗口和框架接口，不创建第二个窗口，也不改变文件打开、保存或文档渲染逻辑。它只在启动初始化分支执行一次，不放进定时检查、自动保存或每次渲染中，避免反复把窗口带到前台。

没有增加 `setTimeout` 或固定等待时间。显示动作依赖实际初始化完成，而不是猜测机器需要多少毫秒。文件打开失败时，现有流程会捕获并显示错误，启动仍能继续到窗口显示步骤。

## 5. 如何验证

### 原生冷启动回归

先正常退出 OpenMind，在项目根目录执行：

```sh
sh scripts/build-macos.sh
sh scripts/test-startup.sh "$PWD/build/bin/OpenMind.app" "$PWD/README.md"
sh scripts/test-startup.sh "$PWD/build/bin/OpenMind.app" "$PWD/examples/灵感.mind.md"
codesign --verify --deep --strict build/bin/OpenMind.app
```

`scripts/test-startup.sh` 编译并运行原生探针，通过系统打开指定文件，测量从发起请求到目标进程窗口进入屏幕窗口列表的时间。超过 **1500 ms** 判失败；15 秒仍无窗口则超时。1500 ms 是本机回归预算，不是所有设备的统一性能承诺。

脚本会正常退出它启动的应用，不强制结束进程；如果已有 OpenMind 运行则拒绝测量。测试会真实打开文档，因此目录会进入最近工作区。测试期间不要手动操作应用，也不要同时运行其他会抢占窗口的 UI 测试。

该探针只能判断窗口出现，不能证明正文已经正确绘制。必须结合下面的前端回归，并在打包应用中确认正文显示正常。

### 前端与功能回归

```sh
node scripts/test-external-open.mjs
node --test frontend/test/*.test.js
go test -race ./...
```

外部打开回归在真实 WebKit 中运行前端，但模拟后端及窗口接口。它验证启动显示调用恰好发生一次，调用时 Markdown 正文区域已显示并包含目标内容，同时覆盖运行中打开、切换前保存、忙碌请求保留、跨工作区和打开失败后的原文档保留。

本次验证结果：原生冷启动、外部打开回归、81 项前端测试、Go race 测试、299 项原生 WebKit 节点模式检查及包签名校验通过。

额外运行的 mind 综合回归在“设置保存时布局与滚动位置保持不变”检查失败。通过测试服务临时移除本次 `WindowShow()` 调用后，同样失败；确认该失败并非本次调用引入，未在本次修改中处理。不能将此次结果描述为所有测试全部通过。

## 6. 以后如何避免

1. **把“窗口出现”作为启动验收的一部分。** 前端 ready、Go 服务启动和 Dock 图标都不足以代表用户已经能看到内容。分别测内容就绪和原生窗口出现，避免优化错层。
2. **启动完成时明确请求显示。** 保留本次收尾调用及其顺序。以后重构启动流程、文件打开队列或工作区恢复时，确保普通启动、指定文件启动及错误提示路径都能完成窗口显示。
3. **同时保留两层回归。** 原生探针捕获系统文件打开至窗口出现的延迟；WebKit 回归检查显示请求时正文状态。单独依赖任一层都会留下盲区。
4. **发布前测试真正的冷启动。** 正常退出应用后，从系统打开 `.md` 和 `.mind.md`，再检查运行中打开其他文件。仅使用开发服务器、前端刷新或已经运行的进程，覆盖不到本次问题。
5. **升级后重测打包产物。** 升级 Wails、macOS 或调整窗口生命周期时，复测上述场景；耗时异常先分段定位，不直接叠加等待、提前显示空窗口或反复强制激活。
6. **确认验证的是新包。** OpenMind 保持单实例；旧安装版仍在运行时，启动新包可能只激活旧进程。打包通过后仍需退出旧版、手动替换安装包，再验证访达文件关联实际启动的版本。
